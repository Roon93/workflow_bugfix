# workflow_bugfix 使用指南

## 快速开始

### 1. 安装

**联网环境：**

```bash
# 克隆仓库
git clone git@github.com:Roon93/workflow_bugfix.git
cd workflow_bugfix

# 安装依赖
npm install
```

**离线/内网环境：**

```bash
# 克隆仓库
git clone <仓库地址>
cd workflow_bugfix

# 重新编译原生模块（依赖已打包，无需联网）
npm rebuild
```

> 内网环境需确保：`gcc/g++ >= 9`、`make`、`python3 >= 3.6`

### 2. 配置 Claude Code

将插件添加到 Claude Code：

```bash
# 方法 1：符号链接（推荐）
ln -s $(pwd) ~/.claude/plugins/workflow_bugfix

# 方法 2：复制到插件目录
cp -r . ~/.claude/plugins/workflow_bugfix
```

重启 Claude Code 使插件生效。

### 3. 初始化项目

在你的代码仓库根目录：

```bash
# 创建配置目录
mkdir -p .bugfix

# 配置多仓库（可选）
cat > .bugfix/repos.json << 'EOF'
{
  "repos": [
    {
      "name": "main-repo",
      "path": "./",
      "role": "main",
      "language": "c++",
      "buildSystem": "cmake"
    }
  ]
}
EOF

# 配置日志模式（可选）
cat > .bugfix/log-patterns.json << 'EOF'
{
  "timestampPattern": "\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}",
  "levelPatterns": {
    "error": ["ERROR", "ERR", "FATAL"],
    "warn": ["WARN", "WARNING"]
  },
  "errorCodePattern": "error[_\\s]code[:\\s]*(\\d+)"
}
EOF

# 构建代码索引
/rebuild-index
```

## 使用场景

### 场景 1：修复 Bug

#### 步骤 1：启动 workflow

在 Claude Code 中输入：

```
/bugfix "程序在处理大文件时崩溃，日志显示 segmentation fault"
```

或者提供日志文件：

```
/bugfix "启动时崩溃" --log crash.log
```

#### 步骤 2：确认分析结果

Agent 会分析问题并提出假设：

```
分析结果：
- 问题分类：内存错误
- 关键线索：segmentation fault, 大文件处理
- 根因假设：
  1. 缓冲区溢出
  2. 空指针解引用
  3. 内存未初始化
- 复现策略：代码级（高置信度）
- 相关仓库：main-repo

是否确认？(y/n)
```

输入 `y` 确认，或提供修正意见。

#### 步骤 3：确认上下文范围

Agent 会定位相关代码：

```
上下文范围：
- 相关文件：
  * src/file_processor.c (处理大文件的核心逻辑)
  * src/buffer.c (缓冲区管理)
- 相关符号：
  * process_large_file() - 主处理函数
  * allocate_buffer() - 缓冲区分配
- 调用链：
  main() → process_file() → process_large_file() → allocate_buffer()
- 影响面：3 个文件，5 个函数

是否确认？(y/n)
```

#### 步骤 4：自动编写测试

Agent 会编写复现测试：

```
已创建测试：test/test_large_file.cpp
测试状态：FAILED（符合预期）

测试内容：
- 创建 100MB 测试文件
- 调用 process_large_file()
- 预期：正常完成，不崩溃
- 实际：segmentation fault

继续修复？(y/n)
```

#### 步骤 5：TDD Loop 自动修复

Agent 进入 TDD Loop（最多 5 轮）：

```
Round 1:
- 修改：src/buffer.c:45 增加边界检查
- 测试：FAILED（仍然崩溃）

Round 2:
- 修改：src/file_processor.c:123 修正缓冲区大小计算
- 测试：PASSED ✓

修复成功！
- 改动文件：2 个
- 改动行数：+8 -2
- Loop 轮数：2
```

#### 步骤 6：回归验证

Agent 自动运行回归测试：

```
回归测试结果：
- 单元测试：45/45 通过 ✓
- 集成测试：12/12 通过 ✓
- 影响面分析：
  * 直接影响：2 个文件，5 个函数
  * 间接影响：1 个文件，2 个函数
  * 风险等级：低

验证通过！
```

#### 步骤 7：查看报告

```
/status

Workflow 状态：
- ID: bugfix-001
- 类型：bugfix
- 当前阶段：OUTPUT（已完成）
- 耗时：8 分钟
- Loop 轮数：2/5

输出文件：
- state/output/result.json（结构化结果）
- state/output/report.md（可读报告）
```

### 场景 2：开发新功能

#### 启动 feature workflow

```
/feature "添加用户认证功能，支持用户名密码登录"
```

流程与 bugfix 类似，但侧重于：
1. **需求澄清**：明确功能边界、输入输出、约束条件
2. **测试先行**：编写功能测试（failing test）

## 高级用法

### 多仓库协同

配置 `.bugfix/repos.json`：

```json
{
  "repos": [
    {
      "name": "firmware-core",
      "path": "./",
      "role": "main",
      "language": "c++",
      "buildSystem": "cmake"
    },
    {
      "name": "driver-usb",
      "path": "../driver-usb",
      "role": "dependency",
      "language": "c",
      "buildSystem": "make"
    },
    {
      "name": "protocol-lib",
      "path": "../protocol-lib",
      "role": "dependency",
      "language": "c++",
      "buildSystem": "cmake"
    }
  ],
  "crossRepoIndex": true,
  "indexStrategy": "incremental"
}
```

启动 bugfix 时，Agent 会：
1. 在所有仓库创建同名分支
2. 跨仓库检索相关代码
3. 同步提交到所有仓库
4. 统一创建 checkpoint

### 非必现 Bug 处理

对于难以复现的 Bug（如竞态条件、内存泄漏）：

```
/bugfix "偶尔出现内存泄漏，无明确复现步骤"
```

Agent 会采用三级复现策略：

**Level 1（代码级）**：尝试直接复现
- 分析日志和栈帧
- 定位可疑代码
- 编写确定性测试

**Level 2（条件推断）**：推断触发条件
- 分析代码路径
- 识别边界条件
- 编写条件测试（如：大数据量、并发、异常输入）

**Level 3（推测性）**：基于假设修复
- 标记为 `speculativeFix: true`
- 编写假设性测试
- 实施保守修复（如：增加边界检查、资源释放）
- 建议长期监控

#### 重建索引

代码变更后，重建索引以获得最新的代码图谱：

```
# 增量重建（默认，只重建变更文件）
/rebuild-index

# 全量重建
/rebuild-index --full
```

#### 使用 CLI 工具

直接调用 MCP 工具：

```bash
# 搜索文件
node bin/bugfix-cli index:search-files "memory" "allocation"

# 搜索符号
node bin/bugfix-cli index:search-symbols "process_data"

# 追踪调用链
node bin/bugfix-cli index:trace-calls "handle_request" --direction callers

# 分析影响面
node bin/bugfix-cli index:analyze-impact src/core.c src/utils.c

# 解析日志
node bin/bugfix-cli log:parse crash.log

# 提取线索
node bin/bugfix-cli log:extract-clues crash.log --keywords "error" "failed"

# 发现测试
node bin/bugfix-cli test:discover --repos ./ --languages c cpp

# 运行测试
node bin/bugfix-cli test:run test/test_core.cpp --framework gtest
```

```json
{
  "repos": [
    {
      "name": "仓库名称",
      "path": "仓库路径（相对或绝对）",
```

## 工作流阶段详解

### 1. ANALYSIS（分析）
- **输入**：Bug 描述、日志文件
- **输出**：`state/analysis/confirmed.json`
- **内容**：问题分类、关键线索、根因假设、复现策略
- **Checkpoint**：`checkpoint-analysis`

### 2. CONTEXT（上下文）
- **输入**：分析结果
- **输出**：`state/context/scope.json`
- **内容**：相关文件、符号、调用链、影响面
- **Checkpoint**：`checkpoint-context`
- **并发**：3 个 sub-agents（文件/符号/图谱）

### 3. TEST（测试）
- **输入**：上下文范围
- **输出**：`state/reproduce/test-result.json`
- **内容**：复现测试（failing test）
- **Checkpoint**：`checkpoint-test`

### 4. ACCEPTANCE（验收）
- **输入**：测试结果
- **输出**：`state/acceptance/confirmed.json`
- **内容**：验收标准、风险区域、约束条件
- **Checkpoint**：`checkpoint-acceptance`

### 5. FIX（修复）
- **输入**：验收标准
- **输出**：`state/fix/success.json`
- **内容**：TDD Loop（最多 5 轮），改动文件、测试结果
- **Checkpoint**：`checkpoint-fix`

### 6. VERIFY（验证）
- **输入**：修复结果
- **输出**：`state/verify/report.json`
- **内容**：回归测试、影响面分析、风险评估
- **Checkpoint**：`checkpoint-verify`
- **并发**：3 个 sub-agents（单测/集成/影响面）

### 7. OUTPUT（输出）
- **输入**：验证报告
- **输出**：`state/output/result.json` + `report.md`
- **内容**：完整报告、建议、注意事项

## 常见问题

### Q1：索引构建很慢怎么办？

**A**：使用增量索引（默认）。只有首次构建较慢，后续只重建变更文件。

```bash
# 首次构建（可能需要几分钟）
/rebuild-index

# 后续增量更新（< 2 秒）
/rebuild-index
```

### Q2：如何跳过某个阶段？

**A**：不建议跳过阶段。如果必须，可以手动创建该阶段的输出文件，然后推进：

```bash
# 手动创建输出文件
mkdir -p state/test
echo '{"status":"passed","testFile":"test/manual.cpp"}' > state/test/test-result.json

# 推进到下一阶段
node bin/bugfix-cli workflow:advance ACCEPTANCE
```

### Q3：TDD Loop 一直失败怎么办？

**A**：
1. 检查 `state/fix/attempt-*.json` 查看每轮尝试
2. 如果检测到重复修改，Agent 会自动停止
3. 手动回退到 CONTEXT 阶段，重新定位问题：
   ```
   /rewind checkpoint-context
   ```

### Q4：如何处理多人协作？

**A**：
1. 每人在独立分支工作
2. 使用不同的 workflow ID
3. 定期同步主分支
4. 合并前运行完整验证

### Q5：支持哪些测试框架？

**A**：
- **C/C++**：gtest, catch2
- **TypeScript/JavaScript**：jest, vitest, mocha
- **Python**：pytest, unittest

### Q6：如何自定义 Agent 行为？

**A**：修改 `agents/*.md` 文件中的 Agent 定义。重启 Claude Code 生效。

## 最佳实践

### 1. 定期重建索引

代码变更后及时重建索引：

```bash
# 每次 pull 代码后
git pull && /rebuild-index

# 或设置 git hook
echo '/rebuild-index' > .git/hooks/post-merge
chmod +x .git/hooks/post-merge
```

### 2. 保持 Checkpoint 清洁

定期清理旧 checkpoint：

```bash
# 查看所有 checkpoint
git tag | grep checkpoint

# 删除旧 checkpoint
git tag -d checkpoint-old-1 checkpoint-old-2
```

### 3. 使用描述性 Bug 描述

好的描述：
```
/bugfix "在处理 UTF-8 编码的日志文件时，程序崩溃。日志显示 'invalid byte sequence'，发生在 parse_log() 函数。测试文件：test_utf8.log"
```

差的描述：
```
/bugfix "程序崩溃"
```

### 4. 验收标准要具体

在 ACCEPTANCE 阶段，提供具体的验收标准：

```
验收标准：
1. 能正确处理 UTF-8 编码的日志文件
2. 能处理包含特殊字符的日志行
3. 不崩溃，不丢失数据
4. 性能不低于原实现
5. 通过所有现有单元测试
```

### 5. 监控 Loop 轮数

如果 Loop 超过 3 轮仍未成功，考虑：
1. 问题定位是否准确？
2. 测试是否过于严格？
3. 是否需要人工介入？

## 故障排查

### 问题：Agent 无响应

**解决**：
1. 检查 Claude Code 是否正常运行
2. 查看 `state/workflow.json` 确认当前阶段
3. 使用 `/resume` 恢复

### 问题：索引查询无结果

**解决**：
1. 确认索引已构建：`ls .bugfix/index.db`
2. 重建索引：`/rebuild-index --full`
3. 检查文件路径是否正确

### 问题：测试执行失败

**解决**：
1. 确认测试框架已安装
2. 手动运行测试验证：`npm test` 或 `./build/test`
3. 检查 `state/reproduce/test-result.json` 查看错误详情

### 问题：Git 操作失败

**解决**：
1. 确认仓库路径正确
2. 确认有 git 权限
3. 检查是否有未提交的变更：`git status`
